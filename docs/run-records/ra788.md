# Codex launch attachment and turn acceptance boundary

Refs [harness#788](https://github.com/rickylabs/harness/issues/788),
[harness#784](https://github.com/rickylabs/harness/issues/784),
[atelier-cockpit#955](https://github.com/rickylabs/atelier-cockpit/issues/955).
Baseline: Orchid main `745875c`. Profile: leaf, tier feature.

## Plan & Design

### What the official protocol can and cannot prove

The protocol inventory is the Codex CLI 0.166.0 app-server v2 schema
(`codex app-server generate-json-schema`). Three capabilities are missing upstream:

| Gap constant | Missing official capability | Consequence in Orchid |
| --- | --- | --- |
| `codex-app-server-v2-no-thread-subscriber-acknowledgment` | No request or notification names the connections or clients subscribed to a thread, or announces another client's `thread/resume`. `thread/attachment/*` is content attachment; `thread/loaded/list` returns ids only. | TUI attachment stays proven by the private daemon-log record, labelled `private-daemon-log`, never vendor-native. The unknown fence stays. |
| `codex-tui-no-composer-ready-acknowledgment` | The TUI exposes no programmatic composer-ready acknowledgment. | Herdr `interactive_ready` with idle/done stays the typed-input gate. It reads the screen and is labelled as such. |
| `codex-app-server-v2-no-running-only-resume` | `thread/resume` has no conditional "only if running" flag. | A thread unloaded between the idle read and the rejoin is cold-loaded by Orchid's rejoin. This is accepted debt (below). |

Official signals that do exist are consumed. `thread/resume {threadId, excludeTurns}` rejoins a running
thread. Subscribers then receive `thread/status/changed` (ready), `turn/started|completed` (turn),
`item/started|completed` (item), approval server requests and `serverRequest/resolved` (approval), and
`thread/closed` (exit). `InitializeCapabilities.optOutNotificationMethods` suppresses streaming deltas
per connection. `process/exited` belongs to `process/spawn` and is not used for the TUI.

### Design checkpoint

1. **Public surface.** No CLI, config or public file changes. Private: typed attachment outcomes; typed
   acceptance refusals in the receipt `reason` and journal `class`; journal kinds `subscription`,
   `signal`, `binding` and `pending`; one log line `launch stages ...` per launch.
2. **Vocabulary.** These terms are new:
   - *attachment authority*: the source that proved the attachment.
   - *native capability gap*: an official acknowledgment that upstream does not provide.
   - *acceptance generation*: the one subscribed canonical connection of an acceptance.
   - *native signal*: a ready, turn, item, approval or exit signal, bound to a thread and a generation.
   - *ahead-of-ack*: a signal received while the single submit is in flight.
   - *wake*: a bound signal that triggers an immediate readback.
   - *bounded reconciliation*: a readback at least once per interval, with at most 64 wakes.
   - *stage clock*: the per-launch record of stage durations.
3. **Ports.** The ports are `goalRPC.nextLine` (the frame source), `codexAcceptance.binding`, `submit`,
   `Host.Stages`, and the private resume-record and TUI-process readers behind `Host`.
4. **Constants.** Gap constants, attachment and acceptance outcome constants, signal kinds and classes,
   `acceptanceMaxWakes`, `acceptanceWakeBatch`, `acceptanceFrameLimit`, `acceptanceOptOut`, and stage names.
5. **Slices.** There are five, in this order: plan; attachment boundary and stage clock; acceptance
   signals; stage benchmark; mutation gate and docs.
6. **Deferred.** These are not done here:
   - Replacing the log grammar, the Herdr readiness gate or the cold-load race. Each is blocked on its gap.
   - Answering approvals.
   - Capacity and ingress, which belong to PR137 and PR138.
   - The Cockpit and mobile receipt consumers.
   - A live staged benchmark on a deployed daemon (no deploy).
7. **Contributor path.** Read `cmd/divybot/codex_launch_boundary.go` first.

### Typed outcomes

No row's next action is "submit again".

| Case | Outcome | Next action |
| --- | --- | --- |
| Native acceptance before the submit reply | Signal class `ahead-of-ack`; `accepted` once the readback agrees | Commit (C3) |
| User item not yet listed | `pending-materializing` | Wait for an item signal or the interval, until the deadline |
| Turn signal ahead of the readback | `pending-readback` | Wait for a bounded period |
| Duplicate notification | Class `duplicate`; no turn counted | Continue |
| Changed consumer | `binding-changed`; attachment `consumer-changed` | Refuse |
| Stale generation | `stale-generation` | Refuse |
| Reused process identity | `process-reused` | Refuse |
| Missing capability (rejoin refused) | `wake-capability-missing` | Bounded polling |
| Missing capability (attachment acknowledgment) | Authority `private-daemon-log`, native `missing` | Keep the private proof and the unknown fence |
| Lost submit acknowledgment | `submit-uncertain` | Refuse; unknown after the effect |
| Lost rejoin acknowledgment | `source-gap`, before the effect | Refuse; zero submits |
| Native exit | `native-exit` | Refuse |
| Turn, active status or approval before the submit | `baseline-active`, before the effect | Zero submits |

### Accepted debt

A thread unloaded in the interval between the idle read and the rejoin is cold-loaded by Orchid's
connection. The cost is bounded: a missing TUI is still caught by the pre-effect and post-candidate
occupant and process checks, and by the deadline. It is never a second submit. The debt can be removed
once Codex offers a running-only rejoin.
